Eval Iterations v1–v8

No tuning by vibes: an automated harness over 45 real queries (LLM-as-judge grades every query × top-5 result), every change gets scored — winners stay, losers roll back.

Iteration diary — what each version was thinking

v1 — measure before touching anything

Before tuning, plant the yardstick: score the plain pipeline (two-track recall + RRF + weighted boost) as-is — 0.9307. Optimization without a baseline is self-congratulation.

v2 — greed: four ideas at once, overall regression

Query understanding had four obvious improvements (alias table, expansion damping, dimension filtering, expansion skipping) — all individually right, so ship all four. Result: -0.005. Three queries improved, five got worse, and the ideas interfered — impossible to tell credit from blame.

→ The turn: one variable per round, from then on. That discipline is worth more than any single trick.

v3 — unbundle, keep one: the first big win

Take v2 apart, keep only the keyword alias table (English aliases + 50 Chinese genre words + award terms). +0.02 → 0.9512; signals like "Korean crime thriller", "award-winning", "prison" — previously missed entirely — all landed.

→ Learned: extending the alias table is pure profit with no side effects. Keep feeding it.

v4 — first reranker attempt: faceplant

Intuition said "an extra precision layer must help". Plugged in an English-domain reranker: -0.014, top-5 hit rate down to 0.73.

→ Learned: it learned "relevance" from English data and can't read a Chinese library; "more AI" doesn't mean better.

v5 — query abstraction: helps the vague, hurts the specific

Let the LLM abstract the query ("brutal breakup, what heals" → "heartbreak healing drama") and recall on that too. Vague queries +1, but six specific queries ("Hong Kong cop films", "prison"…) got noise injected. Net loss.

→ The turn: it's double-edged — the question isn't whether to use it, but when.

v6 — same trick, plus a switch: perfect MRR ⭐

Enable abstraction only when the query contains no concrete condition the parser can find. 0.9623 — rank #1 correct on every single query (MRR 1.0).

→ Learned: the real shape of v2's lesson — gating isn't wrong, it has to clamp the smallest possible knob.

v7 — one more try at the English reranker: confirmed, it's the model

Gave it year/region/cast context, switched to position-aware score blending — architecturally all correct, still 0.9368.

→ Learned: architectural patches can't rescue the wrong model. Two failures pinned the diagnosis.

v8 — Chinese-domain reranker: best balance ⭐

Same API surface, swapped in a Chinese-IR-trained bce model. nDCG flat at 0.9625, but top-5 hit rate +0.05 and zero eval failures — the precision layer finally pays rent.

→ Learned: a reranker's language domain beats its architecture; the right model made all of v4/v7's architectural work click into place.

Representative lessons

  • One change at a time — v2 shipped four ideas together and regressed; v3 kept one and gained +0.02.
  • Step-back query abstraction is double-edged — vague queries benefit, specific ones get polluted; v6's "only when the parser finds nothing concrete" gate reached MRR 1.0.
  • A reranker's language domain beats its architecture — the same API lost twice with an English-domain model; the Chinese-domain bce immediately gained nDCG +0.026, P@5 +0.10.

Appendix: a thriftier yardstick — the judge's model and hardware

The grader (LLM judge) was a local model throughout. Why not cloud? One eval round is 45 queries × top-5 = up to 225 gradings; eleven rounds approach 2,500 calls — free cloud tiers hit rate limits instantly and would fight the product itself for quota. A local judge has zero marginal cost, reruns anytime, and is reproducible (same model, same prompt — scores don't drift with a provider's server-side updates).

v1–v8 used a larger MoE model (35B-A3B, on GPU); later a smaller 8B dense model on an NPU re-scored — a different judge is a different yardstick; the numbers aren't comparable with the table above, so they're listed separately:
